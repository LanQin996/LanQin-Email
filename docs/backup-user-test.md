# 部署后的简短实测清单

先验证备份和隔离解密，再决定是否测试覆盖。以下操作由管理员自行选择执行；部署成功不表示已经在现有邮件数据上执行过恢复。

## 先测不覆盖数据的流程

1. 以超级管理员进入备份设置，自行输入并确认备份密码，在独立密码管理器保存；未设置时不能新建或启用计划，不会自动生成。旧 `.env` 公钥不能代替此步骤。历史归档保留当时密码或 age 私钥，不要发到聊天、截图或问题报告里；新密码不会自动改密旧档。`LANQIN_BACKUP_SECRET_KEY` 是配置加密/可信索引主密钥，不是备份恢复密码，不要直接更换已有服务器主密钥。
2. 刷新页面，以超级管理员进入备份设置，添加一个 S3 或 WebDAV 地点。建议使用专属目录或前缀，先保持自动保留清理关闭。当前没有独立「连接测试」入口。
3. 点击「新建备份」，选择该地点。等任务完成，查看每个地点的结果和云端索引状态；记录任务 ID、时间及密文 SHA-256。只有上传成功、索引失败时不是完整成功，应保留报告。
4. 从地点发现云端备份，选择刚才的记录，提交当前管理员登录密码、已启用时的 TOTP 及归档创建时的备份密码进行恢复验证；历史公钥归档改用对应 age 私钥。成功应显示「备份已验证并隔离暂存」。**到这里不会停服务，也不会覆盖当前邮件。** 自动发现仍需原索引主密钥及云端访问权限，不能仅靠备份密码。
5. 如需测试每日计划，选择未来的 `HH:MM` 和明确的 IANA 时区；核对下次触发时间。确认产生实际成功任务后再决定是否保留计划，不必把时间设成过去来试图立即触发。

## 覆盖恢复另行确认

「覆盖恢复」和上面的隔离解密是两个动作。只有在愿意进入维护窗口、接受快照后新数据退出活动数据树，并确认已保留回退材料时，才选择批准计划并点击「停止服务并覆盖恢复」。

- 维护期间页面可能断连，旧会话会被撤销。保留请求编号，服务恢复后重新登录查询；不要因为没收到响应反复提交。
- 默认批准计划不隔离非空 Postfix 队列；队列不安全时应拒绝继续，不要通过清空队列解决。
- 完成后核对一封已有邮件的正文与附件，再测试新邮件收取及 IMAP 登录。UID/UIDVALIDITY 可能重新分配，不承诺不变。
- 显示需要人工恢复时，保留编号、计划和日志，不删除状态文件或重复安装。应用镜像回退与数据回滚不同，不能用旧数据库直接覆盖新收到的邮件。

## 反馈只需这些信息

发送操作步骤、任务/维护请求编号、发生时间、界面语言及脱敏错误截图即可。不要包含私钥、密码、验证码、Cookie、云端凭据或真实邮件正文/附件。

当前仍缺归档压缩、独立连接测试入口和备份失败主动通知；Google 实际授权及完整部署矩阵的状态见 [交付记录](backup-progress.md)。完整机制见 [Web 恢复](backup-web-restore.md) 和 [主机 helper](backup-maintenance-host.md)。
